# Scholar Renewal System tests

| File | What it checks | How to run |
|---|---|---|
| `run.mjs` | Website side of the grade rules (Phase 1): passed / failed / INC / DRP, the school's passing mark (both directions, letter schools), scenarios 7, 8, 9, 10, 13, 15, 26, 27, INC/DRP accepted when a school enters grades, remarks in the CSV, and source guards (one shared rule, readable text). | `node tests/renewal/run.mjs` — no database or browser needed. |
| `outcome_cases.json` | One table of grade → outcome cases, used by BOTH `run.mjs` (website) and `db/run_db_tests.mjs` (database function `_grade_outcome`) so the two can never disagree. | (data file) |
| `db/run_db_tests.mjs` | The Phase 1 database changes in a scratch Postgres (nothing real is touched): passing mark, INC/DRP, remarks, `_grade_outcome`, SDP Complied / Not complied (scenarios 1–3 and Summer), status history, the status-history backfill preview/apply scripts, and that every earlier grades SQL guard still passes. | Needs PGlite once: `npm i --no-save @electric-sql/pglite`, then `node tests/renewal/db/run_db_tests.mjs`. |
| `run.mjs` (Phase 2 part) | Website wording and helpers for renewal: every stage matches the database's list and titles, the semester judged for each term, window open/late/closed by Philippine date, days-left wording, file checks, plain next steps, and source guards (readable text, screens only ask the database, the new tag is wired in the same places). | same command as above |
| `db/run_p2_tests.mjs` | The Phase 2 database in the SAME private database the local demo uses (every real migration file, in memory) with the demo's TEST data, run signed in as scholars / evaluator / counselor with the real `authenticated` role: every scenario of the owner's table that belongs to this phase (1–10, 11–15, 16–18, 19, 20, 21, 22–25, 26–27), apply / resubmit / flag, documents, windows, late applications, INC decisions, the real grade-correction route, confirm / return, notifications, who may do what, and that the migration can be run twice. | `node tests/renewal/db/run_p2_tests.mjs` (about a minute; needs `npm install` once for PGlite) |
| `db/run_p3_tests.mjs` | Phase 3 database checks (88): availability and 10-minute slots, booking / rescheduling / cancelling (12-hour rule, one booking per renewal), no-show and rebooking, Attended + the Daily Record (INC days -> deadline, Summer hard copy), removing booked availability, reminders, permissions, migration twice. Same in-memory demo database as the Phase 2 tests. | `node tests/renewal/db/run_p3_tests.mjs` |
| `phase1_guard.sql` | The same ideas against the **live** (or staging) database, acting as the first school account. | Paste into the Supabase SQL Editor after the Phase 1 migration; every line should say `PASS`. It rolls itself back. |

Scenario numbers refer to the owner's 32-scenario table in the Phase 0 plan.
