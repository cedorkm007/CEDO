# School grades tests

| File | What it checks | How to run |
|---|---|---|
| `run.mjs` | The rules behind manual grade entry: the "Saved: 1.75 · 1st Semester 2026-2027" confirmation, the read-back check that catches "success shown but nothing saved", blank-subject rows, and the Subjects / Graded / GWA numbers in the school's table. | `node tests/school-grades/run.mjs` — no database or browser needed. |
| `rls_round_trip.sql` | Against the **live** database rules: a school account can read back a grade it just saved, can delete it, cannot save for or see another school's scholars. | Paste the whole file into the Supabase SQL Editor and run it. The result is shown as an error message on purpose (it rolls itself back so nothing is kept). Every line should say `PASS`. |
| `periods_guard.sql` | Phase 2, against the **live** database after the periods migration: existing grades are linked to periods, a school can save/change/delete in an Open period and is refused in a Closed, Archived or never-set-up one, a school cannot manage periods, a tagged staff account can. | Same as above — paste into the Supabase SQL Editor; read the report; every line should say `PASS` (or `SKIP`/`INFO`). It uses made-up periods in 2098-2099 and rolls itself back. |

`run.mjs` also covers Phase 2's period helpers (term-name recognition, school-year check, sort order, labels, deadline text).
| `bulk_grades_guard.sql` | Phase 3, against the **live** database after the bulk-validation migration: a grade on the school's own scale is accepted and one outside it refused, a blank grade is accepted, units are stored and non-positive units refused, the bulk save judges each row on its own and refuses another school's scholar. | Same as above — paste into the SQL Editor; every line should say `PASS`. The school must have saved its grading scale (School Portal > Grading System) first; the earlier `rls_round_trip.sql` also needs that from now on, because schools can no longer save a grade without a scale. |

`run.mjs` also covers Phase 3's upload rules: template contents, whole-file rejections (wrong period, closed period, missing columns, no grading scale), per-row errors and warnings (unknown scholar ID, grade off the scale, bad units, duplicates, overwrites, blank-grade handling), the preview counts, the summary line and the error report.
| `gwa_units_guard.sql` | Phase 4, against the **live** database after the units/exclude migration: nothing is excluded by default, a subject saves with units and "Exclude from GWA" and the school reads both back, saving again without the flag keeps it, and a CSV-style bulk save cannot change the flag of an existing subject. | Same as above — paste into the SQL Editor; every line should say `PASS`. Needs the school's grading scale saved first. |

`run.mjs` also covers Phase 4: the units-weighted GWA (weights, no-units = 1 unit, excluded subjects, unresolvable grades, letters, all-blank → "—"), a guard that there is exactly ONE GWA formula in the app and that the school, staff and scholar views import it, the Units box validation, the read-back of units/flag, and the template-placeholder-row fix.

Phase 5 (School Portal design) has no database change and no SQL test. `run.mjs` covers its logic: scholar status (Not set up / Not graded / Complete / Submitted), the summary counts and progress percent, the period-bar status, Submit-grades enabling, year-level ordering and card progress, search + filters, breadcrumbs, the allowed-grades hint, the change-password rules, the Help/Contact details, and two source guards (no readable text under 13px, no leftover low-contrast greys/link blue in the School Portal). The screens themselves were checked in a browser against sample data (see docs/school-grades/PROGRESS.md).

| `submission_guard.sql` | Phase 6, against the **live** database after the submission/audit/documents migration: a school can submit only when every scholar is complete, grades lock after submitting (no add/change/delete), a correction request unlocks one grade once CEDO approves it, the audit trail records the changes, and a school can attach a PDF only for its own scholar. | Same as above — paste into the SQL Editor; every line should say `PASS`. Needs the school's grading scale saved first. If no account has the `scholars_grades_monitoring` tag yet, the approval step is done directly and reported as SKIP for that part. |

`run.mjs` also covers Phase 6's logic: audit-trail wording, Philippine-time dates, document rules (type, 10 MB, 5 per scholar per period) and storage paths that cannot escape the school's folder, Submit-grades readiness, the period-bar status (Submitted / Reopened by CEDO), which rows are editable once locked, correction-request validation, and the Corrections badge.

| `standing_cleanup_guard.sql` | Phase 7, against the **live** database after the standing/clean-up/logins migration: a school can save a retention requirement on its own scale and not outside it; a school sees only its own scholars and cannot merge schools, assign schools, standardize names or set usernames; a sloppily typed school name is saved as the official one; sign-in finds an account by username or email and never by school name; "Forgot password" reveals nothing and keeps one open request per account; CEDO can merge schools (scholars move, old name kept as an alias, duplicate removed); the staff scholar list pages with an exact total. | Same as above — paste into the SQL Editor; every line should say `PASS`. Needs the first school account to have saved its grading scale. It creates two made-up `__Test` schools and rolls everything back. Staff and IT checks are reported as SKIP if no such account exists. |

`run.mjs` also covers Phase 7's logic: scholarship standing (both scale directions, the margin and the boundary values, no GWA / no requirement), school-name matching and merge suggestions, the Excel report (completion, units-weighted GWA, average GWA, submission status, by school / program / period, sheet shape), and source guards (login by username or email, shared rules only, readable text in the new screens).
