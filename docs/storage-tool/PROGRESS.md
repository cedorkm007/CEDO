# Storage Tool — progress

Working rules (owner): each phase on its own branch + PR; NO merge until the owner says "Approved, next phase" for the whole feature's go-live; end each phase with a walkthrough and STOP; plain language; previews must not touch real data (local demo only).

## Decisions (owner, 2026-10-16)
Name **Storage Tool**; access = a NEW staff tool tag `storage_tool` (given by it.admin1; it.admin1 always may); **personal storage** per person, with sharing to other staff (permission chosen per share: view / upload / full edit) and to the public (upload-only links, with a "lock key" = optional password); non-staff = anyone with the link; uploaders cannot see others' files; Trash 30 days; whole storage 200 GB; biggest file 500 MB; only the link creator is notified; local demo first, then one careful real-site trial; no virus scanning in v1; default allowed types PDF, JPG, PNG, DOCX, XLSX; CAPTCHA (Cloudflare Turnstile) built but OFF until a key is added.

## Phase 0 — plan (2026-10-16)
`CEDO_Drive_Phase0_Plan.docx` (CEDO-SQL-exports). Findings: React + Vite on Vercel, Supabase; `it.admin1` is a username not a tag; files in a new private bucket; tus uploads; ZIP in the browser (cap ~500 MB); public upload through edge functions + signed upload URLs (Phase 3).

## Phase 2 — organizing (branch `storage-tool/phase-2`, stacked on phase-1)
- Database — `supabase_migration_storage_tool_p2.sql`: rename, move (no folder into itself; names never overwritten), Trash (a deleted folder is ONE item taking everything inside; restore to the original place or to the top; delete forever = stored files removed by the website under a storage rule that only allows files of the owner's own Trash, then rows removed), search (name, 2+ letters, literal % and _), details, folder tree, subtree (for copy + ZIP), automatic clean-up (`storage_tool_purge_claim/_finish` for the service role + `storage_tool_purge_schedule` hourly timer) and the edge function `supabase/functions/storage-tool-purge` (secret `STORAGE_TOOL_PURGE_SECRET`, deploy with --no-verify-jwt).

- Demo: storage stand-in gained copy, several signed links at once and an automatic purge timer.
- Tests: Phase 2 database 47, website 30 (all Phase 1+2). Browser (demo): rename, move via picker and by drag, copy, ZIP (Reports/…), details, search, delete folder with the counts question, restore, delete forever; axe clean on list, grid, details, selection bar, picker and Trash.

## Phase 3 — sharing (branch `storage-tool/phase-3`, stacked on phase-2)
- Database — `supabase_migration_storage_tool_p3.sql`: `storage_tool_shares` (per person: view < upload < edit, on a folder or a file, inherited down a folder), `storage_tool_links` (upload-only links: 64-hex code, active / paused / revoked / expired, lock key stored only as a PBKDF2 hash made in the browser, end date, files per person, biggest file, allowed types, instructions, ask email / phone, optional sub-folders), `storage_tool_upload_sessions` (one per visit: name / email / phone, count), `storage_tool_public_events` (rate limits, salted address fingerprints). The Phase 1-2 functions were redefined to understand levels (owner 4, edit 3, upload 2, view 1): items added by others belong to the folder's owner; items deleted by an editor go to the OWNER's Trash; editors cannot rename / move / delete the shared top folder. New: `storage_tool_browse`, `_shared_with_me`, `_staff_search`, `_share_set / _share_remove / _shares_of`, `_link_create / _link_update / _link_set_status / _links_list / _link_visitors`, service-role-only `_public_link_get / _public_rate / _public_session_create / _public_session_get / _public_register / _public_mine`, `storage_tool_notify_uploads` (one grouped notice per visit, a minute after the last file) + pg_cron job `storage-tool-notices`. Storage rules now follow the file rows (read by owner / shared level).
- Public side — `supabase/functions/_shared/storageToolPublic.ts` (the rules + one request handler, shared by the edge function, the demo stand-in and the tests) and `supabase/functions/storage-tool-public` (deploy with --no-verify-jwt; secrets `STORAGE_TOOL_IP_SALT`, optional `TURNSTILE_SECRET` + website variable `VITE_TURNSTILE_SITE_KEY`). Actions: info, open, start, finish, mine. The server picks the storage spot (`public/<link>/<file>`), makes a one-time upload address, checks the size and the first bytes (blocks programs, scripts, web pages, SVG; the content must match the ending), and never lets a visitor read, rename, move or delete anything.
- Website: tabs My storage / Shared with me / Upload links / Trash; Share dialog (People at CEDO with a permission per person, Upload link tab), link settings dialog, link cards (copy, QR code + PNG download, who sent files, change, pause / open again, stop for good), "Shared with me" list, permission-aware menus and buttons (look only / add / edit), Move picker limited to the shared folder, "Copy to my storage…", notice banner inside shared folders; public page `/upload/<code>` (`src/publicupload/`, route in `main.tsx`): name, optional email / phone / lock key / Turnstile, drag and drop, progress, per-file results, "what you sent". Notifications of type `storage` in the bell and the notifications list (+ "Open Storage Tool").
- Demo: stand-in for `storage-tool-public` (same handler bundled with esbuild), one-time upload address endpoint, notice timer (15 s).
- Tests: database 46 (Phase 3) + 33 (public handler) ; Phase 1 / 2 database suites still 38 / 47; website 37. Browser (demo): share with edit, link with lock key + email, public page (wrong key refused, PDF / JPG sent, .exe and fake PDF refused), owner sees files + grouped notice, editor sees banner, deletes into the owner's Trash and copies into own storage, pause makes the page say "no longer active"; axe clean on the public page (form + upload), share and link dialogs (the only finding is the existing chat button).
